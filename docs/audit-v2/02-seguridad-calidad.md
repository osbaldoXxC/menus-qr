# Auditoría de Seguridad, Calidad y Rendimiento (Fases 5-6)

## Seguridad (Fase 5)
| ID | Hallazgo | Estado | Severidad | Ubicación | Evidencia | Impacto | Recomendación |
|---|---|---|---|---|---|---|---|
| S1 | Validación de entrada en endpoints públicos de recomendación limitada (sin schema estricto) | PARCIAL | Media | `backend/src/controllers/menuController.js` (`getPublicRecommendations`, `getGlobalRecommendations`) | `req.body` destructurado con defaults; no Zod; `limit` parseado sin tope duro; `allergies`/`craving` forma no validada estrictamente | Payloads malformados, abuso de recursos, comportamientos inesperados | Validar con Zod: tipos, longitudes, arrays máximos, `limit` acotado, whitelist dietas/contextos |
| S2 | Exposición de datos internos/stack en health endpoint | NO CUMPLE | Baja | `backend/src/index.js` `/health` | En error devuelve `error: err.message` | Fuga de detalles de infraestructura | Responder mensaje genérico; log interno detallado |
| S3 | Endpoint global enumera platillos de todos los restaurantes activos sin autenticación | CUMPLE (por diseño público) / Riesgo de scraping | Media | `menuController.getGlobalRecommendations` | Query sin auth retorna catálogo activo multi-restaurante; rate-limit 100/15min en `/api/public` | Extracción masiva de datos/precios si se automatiza | Rate-limit específico más estricto, paginación/cache, monitoreo |
| S4 | Backend envía dataset completo de candidatos al ML en cada request | PARCIAL | Media | `menuController.js` → `axios.post` ML | `dishes: candidateDishes/dishesWithRestInfo` (global puede ser grande) | Latencia/costo, posible DoS lógico por carga | Pre-filtrado en DB, top-K candidatos, paginación/streaming, límites |
| S5 | Fallback JS no aplica dieta/negaciones y filtra alergias por substring | NO CUMPLE | Alta | `menuController.js` fallback en ambas funciones | Solo `if (allergies.some(a => text.includes(...)))`; no usa `diet`, ni negaciones del texto; razones afirman compatibilidad | Recomendaciones incompatibles con restricciones obligatorias cuando ML cae | Replicar reglas mínimas obligatorias en backend (alergias/dieta/negaciones) o fallar seguro (sin resultados inseguros) |
| S6 | ML sin autenticación entre servicios (confianza implícita de red) | NO VERIFICADO/PARCIAL | Media | `ml-service/main.py`, backend axios | CORS `*`, sin auth token/mTLS visible | Si ML expuesto, abuso o inyección de payloads | Restringir red, auth service-to-service, CORS interno |
| S7 | CORS backend con whitelist y validación de origen | CUMPLE | - | `backend/src/index.js` | `origin` callback contra `allowedOrigins`, `credentials:true` | - | Mantener lista mínima por entorno |
| S8 | Headers de seguridad (Helmet) | CUMPLE | - | `backend/src/index.js` | `helmet` con CSP/HSTS/frameguard/noSniff/referrer | - | Ajustar CSP según necesidades reales |
| S9 | Aislamiento por restaurante en endpoint específico | CUMPLE | - | `getPublicRecommendations` | Query `WHERE p.restaurante_id = $1 AND p.activo = true` tras resolver restaurante | - | Mantener |
| S10 | Afirmaciones de seguridad alimentaria no garantizables | NO CUMPLE | Alta | `ml-service/main.py` `generate_reasons`, backend fallback | Mensajes "100% libre..." sin evidencia de trazas/contaminación cruzada ni cobertura completa de ingredientes | Riesgo para usuarios alérgicos | Lenguaje cauteloso: "no se detectaron ingredientes declarados..." y disclaimer de datos |

## Calidad y rendimiento (Fase 6)
| ID | Hallazgo | Estado | Ubicación | Evidencia | Impacto | Recomendación |
|---|---|---|---|---|---|---|
| Q1 | Lógica de recomendación duplicada (ML Python y fallback JS con reglas distintas) | NO CUMPLE | `ml-service/main.py`, `backend/src/controllers/menuController.js` | Implementaciones separadas, criterios y seguridad divergentes | Inconsistencia de resultados y riesgo en fallback | Centralizar reglas obligatorias en backend; fallback determinista seguro |
| Q2 | `socialContext` capturado/transmitido pero sin efecto | NO CUMPLE | FE wizard/services, BE payload, ML modelo | Ningún uso en scoring/filtrado | Complejidad y contrato confuso | Eliminar o implementar con valor medible (decisión de producto) |
| Q3 | Límite de resultados no centralizado | NO CUMPLE | FE `limit:8`, BE 5/6, ML 5 | Valores hardcodeados distintos | Resultados impredecibles | Constante/config única por capa con validación |
| Q4 | Consulta global sin paginación/top-K en DB | PARCIAL | `getGlobalRecommendations` query | `SELECT ... FROM platillos ... ORDER BY created_at DESC` sin LIMIT | Escalabilidad deficiente | Preselección en DB (full-text/categorías) y límite de candidatos |
| Q5 | Normalización/parseo repetido y manejo de datos mixtos | PARCIAL | ML/BE/FE | Múltiples `normalize`, JSON strings/arrays en ingredientes/tags | Bugs por forma de datos | Contrato tipado estricto y normalización en borde |
| Q6 | Bug potencial en scoring ML (bloque dish_type dentro de fuzzy) | PARCIAL | `ml-service/main.py` ~L430-500 | Estructura anidada/indentación sospechosa en rama fuzzy/dish_type; `raw_score += ... * 0.8` tras `break` en bloque | Puntajes incorrectos o ramas inalcanzables | Refactorizar scoring con pruebas unitarias específicas |
| Q7 | Frontend comensales: fallback con datos dummy/hardcodeados de restaurantes | PARCIAL | `DescubrirResultados.tsx` | `FALLBACK_RECOMMENDATIONS` con IDs/URLs fijos | Puede mostrar platos inexistentes en contexto actual si se usa mal | Fallback solo UI (estado vacío/error) sin inventar resultados reales |
| Q8 | Logging con `console.*` disperso | PARCIAL | BE/FE/ML | `console.error/warn/log` en múltiples archivos | Observabilidad inconsistente | Logger estructurado y niveles |
